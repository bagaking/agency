## Context
Agency already compiles most renderer/main code from TypeScript, but several important host-owned modules still live in CommonJS JavaScript with `@ts-nocheck`, especially around:
- Main Agent Harness controller/runner/provider logic
- provider subprocess helpers
- skill-pack orchestration descriptors
- selected support/config scripts

The repo also lacks a single project-level guardrail that says which paths are governed by the "no JS" rule and which are not.

## Goals / Non-Goals
- Goals:
  - make repo-authored governed source TypeScript-only;
  - migrate Harness/runtime JS modules without regressing Electron main behavior;
  - define one validator that rejects future JS reintroduction in governed paths;
  - document the rule in project norms so later agents can recover it from repo state alone.
- Non-Goals:
  - do not attempt to rewrite vendored code, packaged output, or hidden skill assets under `.codex/`;
  - do not require generated build artifacts to stop being JavaScript;
  - do not collapse runtime architecture work and TypeScript migration into one unreviewable mega-change.

## Decisions

### Decision: Govern source roots, not every file in the repo
The no-JS policy should apply to repo-authored implementation roots only:
- `apps/**`
- `pkg/**`
- `scripts/**`

Explicit exclusions:
- generated output (`dist/`, `.electron-build/`, packaged app contents)
- vendored/third-party folders (`node_modules/`, hidden skill payloads such as `.codex/`)

This keeps the policy strict where Agency owns the code, while avoiding false positives on generated/vendor assets.

### Decision: Main Agent Harness migration is the first mandatory slice
The Harness stack is the highest-value migration target because it currently mixes:
- CommonJS runtime modules
- dynamic provider JSON parsing
- audit/failure state handling
- host capability boundaries

These are exactly the places where TypeScript should help most.

Migration target set:
- `apps/editor/electron/services/mainAgentHarness.js`
- `apps/editor/electron/services/mainAgentHarness/**/*.js`

### Decision: Generated JavaScript remains acceptable
The project should distinguish:
- source of truth: TypeScript / declarative config checked into the repo
- build/runtime artifacts: JavaScript generated by compilers/build tools

Therefore:
- checked-in source JS is disallowed in governed roots after migration;
- emitted `.electron-build/**/*.js`, packaged output, and package `dist/**/*.js` remain expected artifacts.

### Decision: Enforce the policy with one repo-local validator
Add one validator command that:
- scans governed source roots for repo-authored `.js`, `.cjs`, `.mjs`;
- ignores generated/vendor paths;
- fails fast with actionable file paths.

This validator should run in normal developer validation, not only in one-off cleanup scripts.

### Decision: Remove `allowJs` from Electron source compilation after migration
Today `apps/editor/tsconfig.electron.json` allows checked-in JS source.
End-state:
- Electron source compilation consumes `.ts` only for repo-authored code;
- any required runtime JS comes from generated output or external tooling, not tracked source.

## Migration Plan
1. Define governed roots + validator.
2. Migrate Harness/main-process JS modules to TS.
3. Migrate remaining repo-authored JS/CJS/MJS under governed roots.
4. Tighten compiler/build config (`allowJs` removal where applicable).
5. Update docs/norms/AGENTS for durable enforcement.

## Risks / Trade-offs
- Risk: packaging hooks and Electron-builder integration may still expect JS filenames.
  - Mitigation: keep TS source but point tooling at emitted JS artifacts, not tracked JS source.
- Risk: a blanket no-JS rule can block necessary config entrypoints.
  - Mitigation: migrate executable/config scripts to TS-driven entrypoints or explicitly carve out only the minimal external-tool exceptions in the validator.

## Open Questions
- Whether any top-level config script must remain non-TS for external tool compatibility, or whether all of them can be driven from emitted TS output.
- Whether the no-JS validator should cover hidden repo directories beyond `apps/`, `pkg/`, and `scripts/`.
